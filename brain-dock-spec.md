# Brain Dock
## Complete Engineering Specification and Build Guide

**Target environment:** Ubuntu 26, X11, i3 window manager  
**Primary language:** Rust  
**UI:** Slint  
**Local LLM:** Qwen3 1.7B, GGUF, Q4 quantization  
**Inference:** llama.cpp with CUDA  
**Primary storage:** SQLite + FTS5  
**Goal:** An instant, floating, local knowledge assistant that searches your files, answers short questions, and opens the exact note, code, app, URL, or video associated with the answer.

---

# 1. Product definition

Brain Dock is not a normal chatbot and should not become one.

Its job is:

> Press one shortcut, ask how you did something, get a concise answer from your own files, then jump directly to the relevant resource.

Typical interaction:

```text
Super + Space

┌────────────────────────────────────────────┐
│ how did I make OBS follow the cursor?      │
└────────────────────────────────────────────┘

                 ↓

┌────────────────────────────────────────────┐
│ You used a fixed crop region centered on   │
│ the cursor, then smoothed its movement.    │
│                                            │
│ obs/cursor-follow.md · Smoothing           │
│                                            │
│ [Note] [Code] [▶ 06:54] [OBS] [Copy]       │
└────────────────────────────────────────────┘
```

Brain Dock has five responsibilities:

1. Index your local knowledge.
2. Retrieve the correct sections quickly.
3. Use a small local LLM to compose an answer.
4. Expose trusted actions attached to the retrieved sources.
5. Learn from your corrections without constantly retraining the model.

It should feel more like Spotlight, Alfred, or a command palette than ChatGPT.

---

# 2. Non-goals

Do **not** initially build:

- a full note editor;
- a web browser;
- a general-purpose autonomous agent;
- cloud sync;
- multi-user accounts;
- a giant vector database;
- a browser-based UI;
- unrestricted shell execution generated by the LLM;
- automatic fine-tuning after every correction;
- Wayland support;
- Windows or macOS support.

The first version is a personal X11+i3 tool.

That constraint is useful. It lets the application integrate deeply with your actual environment instead of carrying portability complexity from day one.

# 3. Design principles

## 3.1 Instant first

The dock must appear immediately.

The LLM, embedding model, database, and file watchers therefore live in a persistent daemon. Showing the dock must never require loading a model.

Target perceived latency:

```text
shortcut → visible dock:       < 50 ms target
keystroke → rendered text:     immediate
query → first search results:  < 100 ms target for normal vaults
query → first answer token:    ideally < 500 ms on warm system
cached query → answer:         effectively immediate
```

These are design targets, not guarantees.

## 3.2 Retrieval is the brain; the LLM is the narrator

The LLM should not be trusted to remember your workflows.

```text
wrong architecture

files → stuff everything into LLM → answer
```

Use:

```text
files
  ↓
structured index
  ↓
retrieval
  ↓
small relevant context
  ↓
LLM
  ↓
answer
```

## 3.3 Actions are data, never hallucinations

The LLM may explain an action, but it must not invent paths, URLs, application identifiers, or shell commands.

Actions are parsed from trusted source metadata and returned separately from generated text.

## 3.4 Local-first

The normal query path should require no internet connection.

## 3.5 Keyboard-first

Every important action needs a keyboard path.

## 3.6 Corrections should improve the system immediately

A correction should first update correction memory. Fine-tuning is a later, batch operation.

# 6. Window behavior on X11 + i3

The dock is a real X11 window, but it should behave like a system overlay.

Desired properties:

- frameless;
- always-on-top;
- floating;
- sticky across workspaces;
- absent from normal tiling layout;
- positioned at top-right of active monitor;
- keyboard focus on summon;
- hidden rather than destroyed when dismissed.

Set a stable class, for example:

```text
WM_CLASS instance = brain-dock
WM_CLASS class    = BrainDock
```

Recommended i3 config:

```i3
for_window [class="BrainDock"] floating enable
for_window [class="BrainDock"] border pixel 0
for_window [class="BrainDock"] sticky enable
```

i3 supports applying commands such as floating and border rules through `for_window` criteria.

Do not use `override_redirect` by default. Letting i3 manage the window is easier for focus, monitor handling, and keyboard behavior. Only test an override-redirect implementation later if i3 interaction becomes a real limitation.

# 7. Positioning

Default configuration:

```toml
[dock]
anchor = "top-right"
margin_top = 22
margin_right = 22
width = 560
input_height = 62
max_answer_height = 520
```

Determine the active monitor in this order:

1. monitor containing the currently focused X11 window;
2. monitor containing the pointer;
3. primary monitor;
4. first detected monitor.

Then calculate:

```text
x = monitor.x + monitor.width - dock.width - margin_right
y = monitor.y + margin_top
```

Slint exposes desktop window position and size APIs; on X11 the application can set a physical screen position. Slint also exposes `always-on-top` and frameless-window properties on supported window managers.

# 10. Core data model

Use stable identifiers so index updates do not destroy relationships.

```rust
pub struct DocumentId(pub i64);
pub struct SectionId(pub i64);
pub struct ActionId(pub i64);
```

## Document

```rust
pub struct Document {
    pub id: DocumentId,
    pub path: PathBuf,
    pub canonical_path: PathBuf,
    pub title: Option<String>,
    pub mime: String,
    pub modified_ns: i64,
    pub size: i64,
    pub content_hash: [u8; 32],
    pub parser_version: u32,
}
```

## Section

A section, not a whole file, is the primary retrieval unit.

```rust
pub struct Section {
    pub id: SectionId,
    pub document_id: DocumentId,
    pub parent_id: Option<SectionId>,
    pub heading: Option<String>,
    pub heading_path: Vec<String>,
    pub body: String,
    pub start_line: u32,
    pub end_line: u32,
    pub order_index: u32,
    pub token_estimate: u32,
}
```

Example Markdown:

```md
# OBS

## Cursor follow
...

### Smoothing
...
```

Becomes roughly:

```text
OBS
OBS / Cursor follow
OBS / Cursor follow / Smoothing
```

This gives precise retrieval and precise `nvim +line` navigation.

# 13. Parsing pipeline

## V1 supported formats

Start with:

1. Markdown
2. plain text
3. source code

Then add:

4. PDF
5. HTML
6. JSON/YAML/TOML
7. subtitles/transcripts

Do not block V1 on perfect PDF support.

## Markdown parser

Extract:

- front matter;
- headings;
- heading hierarchy;
- paragraphs;
- fenced code;
- list items;
- links;
- special `@action` metadata;
- source line numbers.

Use a real CommonMark-compatible parser rather than hand-written regex for document structure.

## Source code parser

Use tree-sitter later to index semantic units such as:

```text
file
class / struct
function
method
module
impl block
```

A code question should retrieve the function or type, not a random fixed-size chunk.

# 14. Chunking strategy

Avoid naïve fixed 500-token chunks as your main strategy.

Use semantic units first.

For Markdown:

```text
heading section → retrieval unit
```

If a section is too large:

```text
section
  ↓
paragraph-aware subchunks
  ↓
small overlap only where necessary
```

Suggested initial parameters:

```toml
[indexing]
max_section_tokens = 700
subchunk_target_tokens = 450
subchunk_overlap_tokens = 60
```

Store parent-child relationships so a retrieved subchunk can display its real heading path.

# 15. SQLite schema

One database is enough for the first version.

Example:

```sql
CREATE TABLE documents (
    id              INTEGER PRIMARY KEY,
    path            TEXT NOT NULL UNIQUE,
    canonical_path  TEXT NOT NULL,
    title           TEXT,
    mime            TEXT NOT NULL,
    mtime_ns        INTEGER NOT NULL,
    size_bytes      INTEGER NOT NULL,
    content_hash    BLOB NOT NULL,
    parser_version  INTEGER NOT NULL,
    indexed_at      INTEGER NOT NULL
);

CREATE TABLE sections (
    id              INTEGER PRIMARY KEY,
    document_id     INTEGER NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
    parent_id       INTEGER REFERENCES sections(id) ON DELETE CASCADE,
    heading         TEXT,
    heading_path    TEXT NOT NULL,
    body            TEXT NOT NULL,
    start_line      INTEGER NOT NULL,
    end_line        INTEGER NOT NULL,
    order_index     INTEGER NOT NULL,
    token_estimate  INTEGER NOT NULL
);

CREATE TABLE section_tags (
    section_id INTEGER NOT NULL REFERENCES sections(id) ON DELETE CASCADE,
    tag        TEXT NOT NULL,
    PRIMARY KEY(section_id, tag)
);

CREATE TABLE actions (
    id                INTEGER PRIMARY KEY,
    section_id        INTEGER NOT NULL REFERENCES sections(id) ON DELETE CASCADE,
    kind              TEXT NOT NULL,
    label             TEXT NOT NULL,
    target            TEXT NOT NULL,
    line              INTEGER,
    timestamp_seconds INTEGER,
    trusted           INTEGER NOT NULL DEFAULT 1
);
```

## FTS5 table

```sql
CREATE VIRTUAL TABLE sections_fts USING fts5(
    heading,
    heading_path,
    body,
    content='sections',
    content_rowid='id',
    tokenize='unicode61'
);
```

SQLite FTS5 provides full-text search and includes BM25 ranking support. Its `bm25()` function also supports per-column weighting, which is useful for making heading matches more important than body matches.

Example:

```sql
SELECT
    s.id,
    s.heading_path,
    s.body,
    bm25(sections_fts, 8.0, 4.0, 1.0) AS score
FROM sections_fts
JOIN sections s ON s.id = sections_fts.rowid
WHERE sections_fts MATCH ?
ORDER BY score
LIMIT 30;
```

Note: FTS5's BM25 score convention is arranged so better matches sort earlier in ascending order.

# 16. Embeddings

Do not make embeddings mandatory for the first successful prototype.

Build retrieval in this order:

```text
V0: FTS5 only
V1: FTS5 + metadata filters
V2: embeddings + hybrid retrieval
V3: reranker
```

This prevents you from spending days optimizing semantic search before proving the UX.

## Embedding interface

```rust
pub trait Embedder {
    fn dimension(&self) -> usize;
    async fn embed_query(&self, text: &str) -> Result<Vec<f32>>;
    async fn embed_documents(&self, texts: &[String]) -> Result<Vec<Vec<f32>>>;
}
```

Keep the model swappable.

Store:

```sql
CREATE TABLE section_embeddings (
    section_id     INTEGER PRIMARY KEY,
    model_id       TEXT NOT NULL,
    model_revision TEXT NOT NULL,
    dimensions     INTEGER NOT NULL,
    vector_blob    BLOB NOT NULL,
    FOREIGN KEY(section_id) REFERENCES sections(id) ON DELETE CASCADE
);
```

If the embedding model changes, regenerate vectors in the background.

# 17. Retrieval pipeline

Final pipeline:

```text
query
  ↓
normalize
  ↓
context enrichment
  ↓
correction-memory lookup
  ↓
┌─────────────────────────────┐
│ lexical FTS5 / BM25         │
│ semantic vector retrieval   │
│ metadata/context filters    │
└──────────────┬──────────────┘
               ↓
        reciprocal-rank fusion
               ↓
          optional reranker
               ↓
             top N
               ↓
       context pack builder
               ↓
            Qwen3
```

## Query normalization

Do lightweight deterministic cleanup:

- trim whitespace;
- normalize repeated spaces;
- preserve quoted phrases;
- preserve code symbols;
- preserve filenames;
- do not aggressively stem programming identifiers.

Do not use the LLM merely to rewrite every query. That adds latency.

# 18. Desktop context enrichment

This is one of the most valuable custom features.

When the user summons Brain Dock, capture:

```rust
pub struct DesktopContext {
    pub active_window_id: Option<u32>,
    pub wm_class: Option<String>,
    pub window_title: Option<String>,
    pub pid: Option<u32>,
    pub process_name: Option<String>,
    pub cwd: Option<PathBuf>,
    pub workspace: Option<String>,
}
```

On X11, read the active window through EWMH properties such as `_NET_ACTIVE_WINDOW`, then inspect relevant properties from that window. Use the window PID where available to inspect `/proc/<pid>`.

Examples:

```text
Blender active
query = "how did I mirror bones?"

retrieval boost:
  tags:blender
  app:blender
```

```text
Ghostty + nvim active
cwd = ~/projects/my-game
query = "where is the sprite importer?"

retrieval boost:
  path under ~/projects/my-game
```

Context should **boost** ranking, not hard-filter it unless the user explicitly asks for the current project.

# 19. Hybrid ranking

Keep scores from different systems independent; combine ranks rather than trying to normalize unrelated raw scores initially.

Reciprocal Rank Fusion is simple:

```text
RRF(d) = Σ 1 / (k + rank_i(d))
```

Use something like `k = 60` initially.

Additional boosts:

```text
+ current application match
+ current project path match
+ heading exact match
+ user-confirmed correction source
+ recently used source
- stale/archived directory
```

Keep all weights in config so you can benchmark rather than hard-code intuition.

---

# 20. Reranking

Do not add a reranker until hybrid search is working.

A reranker receives approximately the best 20–40 candidate sections and returns a better ordering.

Interface:

```rust
pub trait Reranker {
    async fn rerank(
        &self,
        query: &str,
        candidates: &[Candidate],
    ) -> Result<Vec<ScoredCandidate>>;
}
```

Make it optional:

```toml
[retrieval.reranker]
enabled = false
```

You should be able to measure whether the reranker improves your own retrieval test set before accepting its latency cost.

# 21. Local LLM

Use **Qwen3 1.7B** as the initial answer model.

The Qwen3 family includes a dense 1.7B model and supports both thinking and non-thinking behavior. For this application, prefer the fast/non-thinking mode for normal retrieval answers; the source context should already contain the solution.

Run it through llama.cpp using GGUF. llama.cpp uses GGUF as its model format and supports local inference with GPU offloading when built with the appropriate backend.

Recommended initial model config:

```toml
[llm]
backend = "llama.cpp"
model = "~/.local/share/brain/models/qwen3-1.7b-q4.gguf"
context_tokens = 4096
max_output_tokens = 350
temperature = 0.15
top_p = 0.85
keep_loaded = true
```

Do not give the model a giant context window just because it supports one. Short contexts reduce prompt-processing time and discourage irrelevant synthesis.

# 22. LLM process architecture

You have two implementation choices.

## Option A — llama-server child process

The daemon launches `llama-server` and communicates through localhost HTTP.

Advantages:

- easiest to prototype;
- llama.cpp can be upgraded independently;
- easy streaming;
- easy debugging with curl.

Disadvantages:

- extra process;
- HTTP serialization overhead, although tiny compared with model inference.

Use this first.

## Option B — direct C API / Rust binding

Embed llama.cpp into `brain-daemon`.

Advantages:

- one process;
- maximum lifecycle control;
- potentially cleaner packaging later.

Disadvantages:

- FFI/build complexity;
- tighter coupling to llama.cpp changes.

Move here only if you have a reason.

# 23. Prompt contract

The system prompt should be extremely restrictive.

Example:

```text
You are the answer composer for a local personal knowledge search engine.

RULES:
1. Answer primarily from the supplied sources.
2. If the sources do not contain enough information, say that clearly.
3. Do not invent file paths, commands, URLs, timestamps, application names,
   or source locations.
4. Keep the response concise and operational.
5. Prefer exact steps when the source describes a procedure.
6. Do not mention actions that are not present in ACTIONS.
7. Do not claim something was found unless it appears in SOURCES.
```

Then send structured context:

```text
QUESTION:
how did I make OBS follow the cursor?

DESKTOP CONTEXT:
active_app=obs

SOURCES:
[1]
path=workflows/obs.md
heading=Cursor Follow > Smoothing
lines=41-63
text=...

[2]
...

ACTIONS:
A1 OpenNote workflows/obs.md line=41
A2 OpenVideo https://... timestamp=414
A3 LaunchApp obs
```

The model returns answer text only.

The UI renders actions from your trusted `Action` records, not from model output.

# 26. IPC

Use a Unix domain socket under:

```text
$XDG_RUNTIME_DIR/brain/brain.sock
```

Do not use `/tmp/brain.sock` as the final design.

Example protocol framing:

```text
4-byte little-endian payload length
MessagePack payload
```

or JSON Lines during development.

Start with JSON Lines because it is inspectable:

```json
{"type":"query","id":"...","text":"how did I..."}

{"type":"token","id":"...","text":" used"}
```

Move to MessagePack only if profiling shows a reason.

# 28. File watching

Use filesystem notifications for fast incremental indexing.

Workflow:

```text
file changed
   ↓
debounce
   ↓
stat + content hash
   ↓
unchanged? → stop
   ↓
parse changed file
   ↓
transaction:
  replace sections
  update FTS
  update actions
   ↓
embedding queue
   ↓
commit
```

Important behaviors:

- debounce editor save storms;
- recognize atomic-save rename patterns;
- do not re-index unchanged content based on mtime alone;
- batch bursts into one DB transaction;
- embed asynchronously after lexical index is ready.

This means a newly saved note is searchable through FTS before its vector embedding has finished.

# 33. Correction memory

This is how the assistant learns immediately.

When an answer is wrong:

```text
Ctrl+E
   ↓
user edits answer
   ↓
store correction
   ↓
future similar query retrieves correction first
```

Schema:

```sql
CREATE TABLE corrections (
    id                  INTEGER PRIMARY KEY,
    question            TEXT NOT NULL,
    normalized_question TEXT NOT NULL,
    bad_answer          TEXT,
    good_answer         TEXT NOT NULL,
    created_at          INTEGER NOT NULL,
    updated_at          INTEGER NOT NULL,
    active              INTEGER NOT NULL DEFAULT 1
);

CREATE TABLE correction_sources (
    correction_id INTEGER NOT NULL,
    section_id    INTEGER NOT NULL,
    PRIMARY KEY(correction_id, section_id)
);
```

Also embed corrections if semantic retrieval is enabled.

A strong correction match can be inserted at the top of the answer context with a marker:

```text
USER-CONFIRMED CORRECTION
```

Do not blindly return it forever: if its source file changed later, mark the correction as potentially stale.

# 34. Feedback model

Every answer can receive:

```text
✓ correct
✗ wrong
✎ edited
```

Store:

```sql
CREATE TABLE query_history (
    id                 TEXT PRIMARY KEY,
    query              TEXT NOT NULL,
    answer             TEXT,
    created_at         INTEGER NOT NULL,
    latency_ms         INTEGER,
    feedback           TEXT
);

CREATE TABLE query_sources (
    query_id     TEXT NOT NULL,
    section_id   INTEGER NOT NULL,
    lexical_rank INTEGER,
    semantic_rank INTEGER,
    final_rank   INTEGER,
    PRIMARY KEY(query_id, section_id)
);
```

This history becomes your evaluation and future training dataset.

# 35. Fine-tuning strategy

Fine-tuning is **not** the first mechanism for storing knowledge.

Use:

```text
facts/workflows     → documents + RAG
immediate fixes     → correction memory
behavior/style      → eventual LoRA fine-tuning
```

Good training examples:

```text
bad: makes up commands
correct: explicitly says source did not contain a command

bad: long generic explanation
correct: concise exact steps from retrieved source

bad: ignores newest workflow
correct: selects newest current source
```

Bad reason to fine-tune:

```text
"My Blender shortcut is Alt+E."
```

That fact belongs in the knowledge store because it may change.

Only start LoRA experiments after you have a meaningful curated set of real corrections, plus a held-out validation set.

# 36. Caching

Use multiple caches rather than one generic response cache.

```text
L1 query normalization cache
L2 query embedding cache
L3 retrieval result cache
L4 prompt/context cache metadata
L5 final-answer cache
```

## Retrieval cache key

Include:

```text
normalized_query
active_app context bucket
index_generation
retrieval_config_version
```

When the index changes, increment an `index_generation` counter.

Do not invalidate everything just because one unrelated file changed forever; V1 can use global generation invalidation, then later move to source-aware invalidation.

## Answer cache key

Include:

```text
retrieval result IDs + section content hashes
LLM model ID
prompt version
generation parameters
correction version
```

This prevents stale cached answers from surviving document changes.

# 37. Performance strategy

Keep hot resources alive:

```text
brain-daemon process
├── SQLite connections open
├── FTS index warm through OS page cache
├── embedding model loaded
├── Qwen model loaded
└── caches resident
```

Do not load Qwen when the dock appears.

## Query latency budget

A useful profiling breakdown:

```text
IPC                    1–5 ms
context collection     1–10 ms
FTS search             target <20 ms
vector query           target <30 ms
fusion/ranking         target <10 ms
prompt build           target <10 ms
LLM first token        dominant cost
UI token rendering     incremental
```

Add tracing from the beginning.

A source can become obsolete.

Add optional metadata:

```md

---
```

Supported statuses:

```text

```

Ranking should strongly penalize `obsolete` and `archived` unless explicitly requested.

This will prevent your assistant from blending old and new workflows.

# 48. Security boundaries

The local LLM receives text that may contain malicious instructions. Treat every indexed document as untrusted prompt content.

The model cannot:

- directly execute commands;
- create actions;
- alter database records;
- launch applications;
- delete files;
- modify notes;
- access arbitrary files outside indexed context through tools.

Only application code performs actions from trusted parsed metadata.

For V1, clicking an `OpenFile` or `OpenUrl` action is safe enough to execute directly because it was explicitly indexed from the user's content. Destructive actions should not exist.

# 57. Answer evaluation

Separate two failures:

```text
retrieval failure:
correct source never reached the LLM

answer failure:
correct source was retrieved, but LLM composed the wrong answer
```

This distinction tells you what to fix.

If retrieval is wrong, fine-tuning Qwen is mostly irrelevant.

If retrieval is correct but answer composition is repeatedly wrong, improve prompting or eventually LoRA-train behavior.

# 61. Example end-to-end data flow

Source:

```md

## Follow cursor

Use a fixed 720×720 capture rectangle. Read cursor coordinates and move the
rectangle target to keep the pointer near the center.

### Smoothing

smoothing before updating the OBS crop transform.

@file ~/projects/obs-follow/src/smoothing.rs:42
```

```text
  path = ~/brain/obs.md

  OpenFile obs.md:12
```

```text
[Note] [Code] [▶ 06:54] [OBS]
```

3. retrieval uses structured sections;
4. actions are trusted metadata;
5. LLM is only an answer composer;
6. corrections are separate memory;
7. every subsystem is measurable.
